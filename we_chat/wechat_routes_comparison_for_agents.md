# 微信聊天记录解析路线对比文档（供 Claude / Codex 决策）

## 1. 文档目的

我们当前的业务目标不是简单备份聊天记录，而是要把微信聊天数据沉淀成可复用的话术库。  
目标链路是：

1. 按会话导出聊天记录  
2. 对导出结果做脱敏  
3. 做场景划分、话术标签化  
4. 最终沉淀为“达人建联话术库”

当前需要在两条技术路线之间做判断：

- 路线 A：基于 **WeFlow 风格的 PC 微信运行态/本地数据读取路线**
- 路线 B：基于 **WechatExporter 风格的移动端备份解析路线**

本文件的目标是帮助后续工程代理（Claude / Codex）理解两条路线的：
- 数据入口
- 实现方式
- 风险点
- 开发复杂度
- 对我们业务目标的匹配度
- 应优先验证的内容

---

## 2. 我们的实际业务诉求

我们并不是为了做一个“微信年度报告工具”，而是为了做一个内部使用的、稳定的、可控的“聊天记录导出与话术库沉淀工具”。

对我们来说，最关键的是：

### 必须实现
- 单会话导出
- 时间范围过滤
- 文本消息优先导出
- 后续支持脱敏
- 后续支持场景分类
- 后续支持话术标签化
- 尽量支持批量、增量沉淀

### 暂时不急
- 漂亮的 GUI
- 年度报告
- 群聊画像
- 语音转写
- 图片/视频解密
- 完整多媒体导出

因此，路线选择的核心判断标准不是“谁功能更炫”，而是：

> 谁更适合稳定地拿到“按会话组织的聊天文本”，并进入后续知识库流程。

---

## 3. 路线 A：WeFlow 风格（PC 微信本地数据 / 运行态读取）

## 3.1 路线概述

WeFlow 是一个本地的微信聊天记录查看、分析与导出工具。  
从公开仓库信息看，它支持：
- 本地实时查看聊天记录
- 本地导出
- 本地 HTTP API
- 联系人 / 会话 / 消息 / 媒体对象访问

对我们有启发的不是“它的 UI”，而是它的分层方式：

1. 密钥 / 数据入口层  
2. 数据读取层  
3. 导出层  
4. 本地 API / 应用层

---

## 3.2 它大概怎么实现

根据公开仓库和 issue 线索，WeFlow 更像是：

### A. 密钥获取阶段
公开 issue 明确出现了这些信号：
- hook 安装成功
- 获取密钥超时
- 原生 hook 失败
- 内存扫描失败
- 缓存计算获取密钥

这说明它在“自动拿到微信数据库密钥”这一步，涉及：
- hook
- 原生 hook
- 内存扫描
- 缓存计算

### B. 数据读取阶段
仓库中存在：
- `wcdbWorker.ts`
- `exportWorker.ts`
- `koffi` FFI 依赖
- 与 `wcdb_api.dll` 相关的 issue

这说明它后续数据读取更像是：
- 通过原生库 / WCDB API 读取数据库
- 而不是简单用标准 sqlite3 打开复制出来的 `.db`

### C. 输出阶段
再将联系人 / 会话 / 消息 / 媒体标准化输出为：
- HTML
- JSON
- TXT
- Excel
- CSV
- 本地 HTTP API

---

## 3.3 这条路线的本质

WeFlow 路线更像是：

> 面向“PC 微信当前运行态”的本地数据读取方案。

关键不是“复制出数据库文件再直接读”，而是：
- 先解决数据库入口（密钥 / 解密 / 运行态能力）
- 再通过原生 API 读库
- 再导出结构化数据

---

## 3.4 这条路线的优点

### 优点 1：最接近我们当前使用场景
我们的媒介同事主要用 PC 微信工作。  
如果这条路线跑通，理论上最贴近实际业务工作流。

### 优点 2：天然支持“按会话导出”
因为它本身就面向 PC 端聊天记录查看与导出，后续很适合抽象为：
- sessions
- messages
- contacts

### 优点 3：容易做成本地服务能力
如果我们未来做自己的工具，这条路线很适合抽象成：
- `GET /sessions`
- `GET /messages?session_id=...`
- `POST /export/session`

### 优点 4：理论上更适合增量沉淀
如果是基于当前 PC 工作号持续导出，后续更容易做增量同步和持续沉淀。

---

## 3.5 这条路线的缺点

### 缺点 1：数据库入口最难
我们已经验证，复制出来的 `.db` 文件不能被标准 sqlite3 直接读取。  
所以这条路线的最大难点不是“表结构”，而是“怎么进库”。

### 缺点 2：自动取密钥/Hook 风险高
如果沿用 WeFlow 的思路去自动取密钥，很可能涉及：
- hook
- 内存扫描
- 注入
- 更高的账号风险与维护复杂度

### 缺点 3：实现复杂
比单纯解析一份备份复杂得多，需要处理：
- 微信版本变化
- 密钥获取方式变化
- 本地库接口变化
- 数据库格式变化

### 缺点 4：不适合直接给媒介同事裸用
这条路线如果不做很好地封装，技术门槛较高。  
不能让媒介同事自己研究 GitHub、自己试错。

---

## 3.6 对我们项目的启发

这条路线最值得借鉴的是：
- 数据分层
- 会话 / 消息 / 联系人标准化对象设计
- 本地 API 能力封装思路

但 **不建议直接照搬它的自动取密钥/Hook 路线** 作为第一版正式产品方案。

---

## 4. 路线 B：WechatExporter 风格（移动端备份解析）

## 4.1 路线概述

BlueMatthew / WechatExporter 本质上是一个：

> “移动端微信备份解析导出器”

它不是读取 PC 微信当前运行态，也不是 Hook 工具。  
它的数据入口是：
- iPhone / iPad 微信
- iTunes 备份
- 或通过设备能力生成备份后再解析

---

## 4.2 它大概怎么实现

从公开仓库结构看，它的核心链路是：

1. 先拿到 iTunes 备份目录  
2. 找到备份中的微信 App 数据  
3. 解析备份中的数据库、资源、plist、索引信息  
4. 重建联系人 / 会话 / 消息 / 资源  
5. 导出为 HTML / Text / PDF

代码结构层面可以概括为：
- `IDeviceBackup.*`
- `ITunesParser.*`
- `WechatParser.*`
- `MessageParser.*`
- `Exporter.*`

这是一条很典型的：
> 数据源解析 -> 结构重建 -> 导出渲染
的路线。

---

## 4.3 这条路线的本质

这条路线更像是：

> 面向“静态备份数据”的离线解析方案。

特点是：
- 不依赖 PC 微信当前运行态
- 不依赖 Hook
- 不需要和 WeChat.exe 交互
- 更像“给我一份备份，我把它解析出来”

---

## 4.4 这条路线的优点

### 优点 1：风险相对低
它不是运行态注入，也不是 Hook 工具。  
相对更适合作为“内部可控工具”路线。

### 优点 2：更容易做离线、批处理
如果同事愿意提供备份，这条路线适合：
- 单次批量导出
- 长期归档
- 离线跑分析
- 离线做脱敏与标签化

### 优点 3：更接近标准数据工程
备份 -> 解析 -> JSON/TXT -> 清洗 -> 入库  
这条链路更像标准 ETL，便于做工程化。

### 优点 4：更容易先做 MVP
如果不要求“实时读取 PC 微信”，而是先要“拿到聊天文本样本做话术库”，这条路线更容易先跑起来。

---

## 4.5 这条路线的缺点

### 缺点 1：流程更麻烦
它需要：
- 手机端
- iTunes 备份
- 备份导出
- 可能的人工操作

对日常使用者来说，不如 PC 微信当前数据直接导出方便。

### 缺点 2：不适合高频实时使用
它更适合：
- 定期批量导出
- 某一时间段统一沉淀

不太适合：
- 现在就看
- 随时导出最新记录
- 高频增量同步

### 缺点 3：和媒介同事日常工作流有偏差
媒介同事主要在 PC 微信上工作。  
如果导出依赖手机备份，使用门槛会更高，组织流程也更重。

### 缺点 4：不一定适合大规模推广给非技术同事
虽然技术风险比 Hook 低，但操作流程并不算轻量。

---

## 4.6 对我们项目的启发

这条路线最值得借鉴的是：
- 数据源 -> 解析 -> 导出 的架构
- 先做文本导出，再做上层分析
- HTML/Text/PDF 只是导出层，不是底层数据层

如果我们最后选择备份路线，建议直接借鉴它的：
- 导出链路设计
- 模块划分
- 中间数据抽象

---

## 5. 两条路线的直接对比

| 维度 | 路线 A：WeFlow / PC 微信运行态 | 路线 B：WechatExporter / 移动端备份 |
|------|--------------------------------|------------------------------------|
| 数据入口 | PC 微信当前数据 / 运行态能力 | 手机微信备份 / iTunes 备份 |
| 是否依赖 Hook 风险 | 可能涉及（至少在取密钥阶段） | 不依赖 Hook |
| 是否依赖数据库解密入口 | 是 | 备份解析为主，路线不同 |
| 实时性 | 高 | 低 |
| 适合增量同步 | 更适合 | 较弱 |
| 技术复杂度 | 高 | 中 |
| 使用复杂度（给媒介同事） | 如果做好封装可低，否则高 | 通常偏高 |
| 风险 | 账号风险 / 兼容性风险 / 维护成本高 | 操作流程重，但技术风险较低 |
| MVP速度 | 如果入口已解决，后面很快；若入口未解决，会卡很久 | 更容易先离线跑通 |
| 对我们业务匹配度 | 高 | 中等偏高 |
| 适合长期产品化 | 高，但入口难 | 中等，偏离实时使用场景 |
| 适合作为短期样本库方案 | 中等 | 高 |

---

## 6. 站在我们业务目标上如何判断

我们要的是：
- 话术库
- 会话导出
- 脱敏
- 标签化
- 后续增量沉淀

所以两条路线并不是非黑即白。

### 如果目标是：尽快拿到样本，做第一批话术库
优先级更高的是：
> **路线 B（备份解析）**

因为它更像一个低风险、离线、可控的数据入口。  
即便流程麻烦，也可能更快拿到“可用于分析的聊天文本”。

### 如果目标是：最终做给媒介同事长期使用的产品
优先级更高的是：
> **路线 A（PC 微信本地导出）**

因为它更贴近真实使用场景。  
但它的前提是：必须先解决数据库入口问题，而且最好避免高风险自动 Hook。

---

## 7. 推荐的项目策略（不是二选一，而是分阶段）

我建议项目策略不要定成“永远只走一条”，而是定成：

## 阶段 1：先拿到可用样本
目标：
- 尽快拿到一批可分析的聊天文本
- 验证脱敏、场景划分、标签化链路

这阶段更适合：
- 优先研究 **备份解析路线**
- 或把它作为低风险样本入口

## 阶段 2：再验证长期产品路线
目标：
- 是否能在 PC 微信侧稳定导出会话
- 是否能支持更贴近日常工作流的导出能力

这阶段再继续推进：
- **PC 微信本地数据路线**
- 但重点是“低风险入口”，不要一开始就 All-in Hook

---

## 8. 我对 Claude / Codex 的建议任务

建议后续工程代理按下面顺序推进，而不是直接选边站：

### 任务 A：先判断备份解析路线是否能更快形成样本库
要回答：
1. 我们实际拿到手机备份的操作链路有多复杂？
2. 备份路线能否稳定导出单会话文本？
3. 备份路线导出的文本是否足够进入脱敏 / 标签化？
4. 作为“第一批话术库样本”是否够用？

### 任务 B：并行判断 PC 微信路线有没有低风险入口
要回答：
1. 我们当前复制出的数据库为什么不能直读？
2. 它更像 SQLite/WCDB 的哪种变体？
3. 除 Hook 外，有没有更低风险的数据库入口？
4. 是否能先只做“手动/半自动”版本，而不是自动取密钥？

---

## 9. 目前我的建议结论

### 最适合短期推进的方案
**先用备份解析路线拿样本。**

原因：
- 风险相对低
- 更容易先跑通“导出文本 -> 脱敏 -> 标签化”
- 适合先验证业务价值

### 最适合长期产品化的方案
**继续保留 PC 微信本地导出路线。**

原因：
- 更贴合媒介同事实际使用方式
- 更适合增量沉淀
- 更适合最终做成“只点几个按钮”的内部工具

---

## 10. 最后一句话

对我们来说：

- **备份解析路线** 更像“低风险样本入口”
- **PC 微信本地导出路线** 更像“长期正式产品路线”

因此最优策略不是简单二选一，而是：

> **短期用备份路线验证话术库价值，长期继续推进 PC 微信导出路线，最终把“样本能力”升级成“日常可用能力”。**
